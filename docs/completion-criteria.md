# Completion criteria

Use the criteria for the requested work together. The owner's latest explicit decisions and accepted result govern; historical experiments do not override them. Keep current task state and private review evidence in the website workspace's `drafts/`, separate from these durable requirements.

## Ready for owner review

1. **Complete the requested scope.** Reconcile the inputs, later additions, and affected records before changing presentation. Preserve accepted content, order, labels, links, and unrelated work. A missing image does not remove an item from the inventory.
2. **Use the accepted result as the reference.** Identify the current page, approved image choices, or the current post's voice before editing. A correction is not permission to redesign adjacent work. An unchanged, explicitly approved presentation is not a blocker merely because a different crop or style could look better; keep that suggestion optional unless the current task reopens the choice. Recheck comparable items when one defect reveals a repeated problem.
3. **Inspect the finished result.** Check changed images against their originals, then inspect the actual affected production-preview page at desktop and phone sizes, in relevant languages and themes. Fix obvious inconsistency, clipping, blur, awkward spacing, broken interaction, and stale copy before handoff. Build success, URL availability, dimensions, and screenshot creation do not establish visual quality.
4. **Resolve defects honestly.** If a requirement is visibly unmet, keep working. When a source search is exhausted or a choice truly needs the owner, state the specific unresolved fact or preference with the available options. A documented exception becomes accepted only when the owner accepts it. Do not label a partial result finished or hide a quality defect among passing technical checks.
5. **Show the requested deliverable.** For car-page work, open the finished page at `/library/#cars`. Keep source receipts and comparisons available; do not substitute a report for the page or repeatedly make the owner find basic defects. For a requested audit, deliver HTML with relevant actual captures and clearly labeled provenance.

## Books and other collection sections

- Keep the accepted library structure and each section's navigation. Complete requested inventory updates without inventing records, ratings, completion status, or public eligibility from private facts.
- Western-book entries use the accepted English titles/descriptions and newer verified English covers from the publisher or authorized bookseller. Check title, author, language, volume, publisher, edition date, and native dimensions. Prefer cohesive current series designs. Aim for 1000 px native width, minimum 600 px; never upscale a thumbnail to meet this requirement. Retain the best verified source and mark an unresolved exception when suitable artwork cannot be found.
- Book frames remain **2:3**, filled by centered cropping without stretching. Preserve accepted reading order and owner reviews; a cover update does not authorize reordering or rewriting them.
- Hotel photo panels put the owner's rating and comment above the photos. Do not insert unsolicited generated blurbs. This component preference does not prohibit composition when the owner asks to write a blog post.
- Prose photos are a separate design decision from product cards. Consider desktop pairs case by case and display prose photos individually on phones. Do not export the car-gallery framing rule to travel posts or impose automatic pairing from orientation alone.
- Preserve the existing Related section and older/newer navigation. Its accepted date restriction excludes posts before 2023 from Related; it does not remove those posts from the archive or change chronological navigation.

## Requested image exploration

When the owner asks to try the installed photo styles, produce the requested distinct treatments independently. For banner exploration, compose the normal portrait or landscape artwork first, then evaluate its banner crop. Preserve generated options under `drafts/` so an earlier choice can still be selected. Artistic-generation permission for these tasks does not change the car gallery's original-photograph default.

## Publication is a separate completion state

- A local preview is ready only after the above checks; a published result additionally requires the authorized commit, push, successful deployment, and verification on the live affected page.
- Reuse explicit approval of the same reviewed scope and bytes, including a recoverable earlier approval. A “push” after the owner reviewed the result authorizes completing the required gate chain; it is not a cue to ask for the same permission again. An initial publication request without a reviewed result does not satisfy the existing preview gate.
- Follow the [preview](../.agents/skills/preview-posts/SKILL.md), [release](../.agents/skills/release-check/SKILL.md), and applicable [ship](../.agents/skills/ship-posts/SKILL.md) workflows. Keep approvals bound to the actual files and hashes. Changed, unreviewed bytes need review; unrelated work never inherits approval.
- Report the actual state: unresolved, ready for review, approved, or deployed. “All checked” and “all resolved” are different claims. A technical GO does not prove that the design or content goal is complete.
